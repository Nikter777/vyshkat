ВышКат

Консольное приложение на Go для учёта парка прокатного транспорта и инвентаря компании «ВышКат».

Проект выполнен в рамках домашнего задания № 1 по дисциплине «Конструирование программного обеспечения».

Возможности

* Приём транспорта на баланс после проверки сервисным центром.
* Отклонение транспорта, не прошедшего проверку.
* Учёт самокатов, обычных и электрических велосипедов.
* Учёт дополнительного инвентаря: шлемов и зарядных станций.
* Подсчёт количества транспорта и инвентаря.
* Расчёт суммарного суточного энергопотребления.
* Вывод транспорта для начинающих пользователей.
* Инвентаризация с отображением названий и инвентарных номеров.

Транспорт считается подходящим для новичков при оценке простоты управления от 6 до 10 включительно.

Запуск

Требуется установленный Go.

Из корневой директории проекта:

go run ./cmd/vyshkat

Запуск тестов:

go test ./...

Проверка покрытия:

go test ./... -count=1 -coverpkg=./... -coverprofile=coverage.out
go tool cover -func=coverage.out

Проверка кода:

go vet ./...

Архитектура

Приложение разделено на четыре части.

internal/domain — предметная модель.

Содержит интерфейсы:

* InventoryItem — объект с инвентарным номером и названием.
* Transport — транспортное средство с оценкой простоты управления.
* EnergyConsumer — объект, потребляющий электроэнергию.

Реализации: Scooter, Bicycle, ElectricBicycle, Helmet, ChargingStation.

Не каждый объект потребляет электроэнергию. Поэтому EnergyConsumer выделен в отдельный интерфейс.

internal/service — бизнес-логика.

Fleet управляет принятым транспортом и дополнительным инвентарём.

Основные методы:

* AddTransport — приём транспорта после проверки.
* AddItem — добавление инвентаря.
* TransportCount и ItemCount — подсчёт объектов.
* TotalEnergyConsumption — суммарное суточное энергопотребление.
* BeginnerFriendly — выбор транспорта с оценкой простоты управления не ниже 6.
* Inventory — получение списка всех объектов на балансе.

ServiceCenter — интерфейс проверки транспорта. DefaultServiceCenter — его стандартная реализация.

Стандартная проверка требует наличия инвентарного номера, названия и оценки простоты управления в диапазоне 1–10. Это упрощённая модель техосмотра, а не полноценная проверка технической безопасности.

internal/di — сборка зависимостей.

Container создаёт и связывает ServiceCenter и Fleet.

Контейнер реализован вручную, без стороннего DI-фреймворка.

cmd/vyshkat — консольное приложение.

Функция run демонстрирует основные сценарии работы системы и выводит отчёты.

Применение SOLID

Single Responsibility Principle — SRP

Каждый компонент отвечает за свою задачу:

* domain описывает объекты предметной области.
* DefaultServiceCenter проверяет транспорт.
* Fleet управляет парком и рассчитывает показатели.
* main.go отвечает за демонстрацию и вывод информации.

Open/Closed Principle — OCP

Для добавления нового вида транспорта достаточно реализовать интерфейс Transport.

Если транспорт потребляет электроэнергию, он дополнительно реализует EnergyConsumer.

Методы Fleet.AddTransport, Fleet.BeginnerFriendly и Fleet.TotalEnergyConsumption не требуют изменения при добавлении нового типа.

Liskov Substitution Principle — LSP

Различные реализации Transport могут использоваться вместо интерфейса Transport.

Например, Scooter, Bicycle и ElectricBicycle передаются в Fleet.AddTransport без изменения алгоритма приёмки.

Interface Segregation Principle — ISP

Интерфейсы разделены по назначению.

Обычный велосипед не обязан реализовывать EnergyConsumer, поскольку не потребляет электроэнергию.

Шлем реализует InventoryItem, но не обязан предоставлять методы транспорта.

Dependency Inversion Principle — DIP

Fleet зависит от интерфейса ServiceCenter, а не от конкретного DefaultServiceCenter.

Реализация передаётся через конструктор NewFleet.

Это позволяет заменять проверку транспорта без изменения Fleet.

Dependency Injection

Зависимости собираются в internal/di/container.go.

NewContainer() создаёт приложение со стандартным сервисным центром.

NewContainerWithServiceCenter(center) позволяет передать другую реализацию интерфейса ServiceCenter.

В тестах используется FakeServiceCenter, который возвращает заранее заданный результат проверки.

Это позволяет независимо проверить принятие и отклонение транспорта.

Сознательное ограничение архитектуры

Принцип открытости/закрытости (OCP) реализован не абсолютно.

Новые типы транспорта можно добавлять без изменения Fleet, однако расширение самого набора операций над парком может потребовать изменения структуры Fleet и его методов.

Для учебного приложения выбран простой подход без дополнительной системы обработчиков и стратегий для каждой операции.

Также приложение использует упрощённую проверку технического состояния транспорта. Реальные диагностические параметры не моделируются.

Расширение системы

Добавление нового транспорта.

Создать структуру, реализующую Transport, а при необходимости — EnergyConsumer. После этого объект можно передавать в Fleet.AddTransport.

Добавление сотрудников.

Можно создать отдельную модель Employee и сервис управления сотрудниками. Сотрудники не должны добавляться в Inventory, поскольку по условию они не учитываются как инвентарь.

Добавление склада.

Можно выделить интерфейс хранилища и реализацию для конкретного склада. Для нескольких складов потребуется определить правила распределения объектов и получения сводных данных.

Тестирование

Тесты находятся в:

* internal/service/fleet_test.go;
* internal/di/container_test.go;
* cmd/vyshkat/main_test.go.

Проверяются:

* Успешная приёмка транспорта.
* Отклонение транспорта после неуспешного техосмотра.
* Вызов сервиса проверки.
* Правило доступности транспорта новичкам, включая граничное значение 6.
* Расчёт энергопотребления.
* Инвентаризация.
* Стандартные проверки сервисного центра.
* Создание зависимостей через контейнер.
* Подмена сервисного центра тестовой реализацией.
* Консольный сценарий приложения.

Для изоляции бизнес-логики используется FakeServiceCenter.

При запуске тестов с -coverpkg=./... суммарное покрытие составило 99,2%.
