ВышКат

Консольное приложение на Go для учёта парка прокатного транспорта и инвентаря компании «ВышКат».

Дисциплина: Конструирование программного обеспечения
Домашнее задание № 1: SOLID, Dependency Injection, юнит-тестирование.

1. Описание проекта

«ВышКат» — учебная система управления парком прокатного транспорта.

Приложение позволяет принимать транспорт после технического осмотра, учитывать имущество компании, рассчитывать суммарное суточное энергопотребление и определять транспортные средства, подходящие начинающим пользователям.

В проекте реализованы следующие виды транспорта:

* Scooter — электросамокат;
* Bicycle — обычный велосипед;
* ElectricBicycle — электровелосипед.

Дополнительный инвентарь:

* Helmet — защитный шлем;
* ChargingStation — зарядная станция.

Сотрудники компании не относятся к инвентаризируемым объектам.

Функциональные возможности

1. Добавление нового транспортного средства в парк.
2. Проверка транспорта сервисным центром перед приёмкой.
3. Принятие или отклонение транспорта по результатам проверки.
4. Подсчёт количества принятого транспорта.
5. Учёт дополнительного инвентаря.
6. Расчёт суммарного суточного энергопотребления.
7. Получение списка транспорта для новичков.
8. Вывод названий и инвентарных номеров всех объектов на балансе.

Транспорт считается подходящим для новичков, если его оценка простоты управления составляет не менее 6 по шкале от 1 до 10.

2. Запуск приложения

Для запуска требуется установленный Go.

Из корневой директории проекта:

go run ./cmd/vyshkat

Запуск всех тестов:

go test ./...

Проверка покрытия:

go test ./... -count=1 -coverpkg=./... -coverprofile=coverage.out
go tool cover -func=coverage.out

Статический анализ:

go vet ./...

Проект использует только стандартную библиотеку Go.

Архитектура разделена на четыре компонента.

3.1. Предметная модель — internal/domain

Пакет содержит структуры, описывающие транспорт и инвентарь, а также интерфейсы, определяющие их возможности.

InventoryItem — объект, имеющий название и инвентарный номер:

type InventoryItem interface {
    InventoryNumber() string
    Name() string
}

EnergyConsumer — объект, потребляющий электроэнергию:

type EnergyConsumer interface {
    DailyEnergyConsumption() float64
}

Transport — транспортное средство:

type Transport interface {
    InventoryItem
    EaseOfUse() int
}

Интерфейсы разделены по назначению.

Например, обычный велосипед реализует Transport, но не реализует EnergyConsumer. Зарядная станция реализует InventoryItem и EnergyConsumer, но не является транспортом.

Это позволяет моделировать объекты без методов, которые им не нужны.

3.2. Бизнес-логика — internal/service

Основной компонент — структура Fleet.

Она отвечает за управление принятым транспортом, дополнительным инвентарём и формирование данных для отчётов.

Основные методы:

Метод	Назначение
AddTransport	Принимает транспорт после техосмотра
AddItem	Добавляет инвентаризируемую вещь
TransportCount	Возвращает количество принятого транспорта
ItemCount	Возвращает количество вещей
TotalEnergyConsumption	Рассчитывает суммарный суточный расход энергии
BeginnerFriendly	Возвращает транспорт с простотой управления ≥ 6
Inventory	Возвращает все объекты на балансе

Транспорт добавляется в парк только при положительном результате проверки.

Если техосмотр не пройден, AddTransport возвращает ошибку ErrInspectionFailed, а объект не попадает в парк.

3.3. Технический осмотр — internal/service/inspection.go

Проверка транспорта вынесена в отдельную зависимость:

type ServiceCenter interface {
    Inspect(transport domain.Transport) bool
}

Стандартная реализация — DefaultServiceCenter.

Она принимает транспорт, если:

* указан инвентарный номер;
* указано название;
* оценка простоты управления находится в диапазоне от 1 до 10 включительно.

Это упрощённая учебная модель техосмотра. Реальные диагностические параметры, износ и техническая безопасность транспорта не моделируются.

3.4. Консольное приложение — cmd/vyshkat

main.go содержит демонстрационный сценарий работы системы.

В нём создаются несколько транспортных средств, включая объект, который не проходит техосмотр.

После этого приложение:

1. Выводит результаты приёмки.
2. Добавляет шлем и зарядную станцию.
3. Показывает количество транспорта и вещей.
4. Рассчитывает суммарное энергопотребление.
5. Выводит транспорт для новичков.
6. Проводит инвентаризацию.

Логика вывода находится в функции run(out io.Writer), что позволяет тестировать консольный сценарий без перехвата стандартного вывода.

4. Применение принципов SOLID

4.1. Single Responsibility Principle (SRP)

Каждый компонент имеет отдельную ответственность.

* domain описывает предметные объекты.
* DefaultServiceCenter выполняет проверку транспорта.
* Fleet управляет парком и рассчитывает показатели.
* Container собирает зависимости.
* main.go демонстрирует работу приложения.

Например, изменение правил технического осмотра не требует изменения алгоритма хранения транспорта в Fleet.

4.2. Open/Closed Principle (OCP)

Система допускает добавление новых видов транспорта без изменения существующей логики управления парком.

Для этого новый тип должен реализовать интерфейс Transport.

Если он потребляет электроэнергию, дополнительно реализуется EnergyConsumer.

Методы AddTransport, BeginnerFriendly и TotalEnergyConsumption продолжают работать с новым типом без изменения своей реализации.

4.3. Liskov Substitution Principle (LSP)

Вместо интерфейса Transport могут использоваться разные реализации:

* Scooter;
* Bicycle;
* ElectricBicycle.

Все они предоставляют методы, необходимые для работы Fleet.

При этом бизнес-логика не зависит от конкретного вида транспорта.

4.4. Interface Segregation Principle (ISP)

Вместо одного большого интерфейса используются несколько небольших:

* InventoryItem;
* Transport;
* EnergyConsumer.

Благодаря этому объекты реализуют только необходимые им возможности.

Например, шлем не обязан предоставлять оценку простоты управления или энергопотребление.

4.5. Dependency Inversion Principle (DIP)

Fleet зависит от абстракции ServiceCenter, а не от конкретной реализации DefaultServiceCenter.

Зависимость передаётся через конструктор:

func NewFleet(serviceCenter ServiceCenter) *Fleet

Это позволяет изменять механизм проверки транспорта независимо от логики управления парком.

Наиболее явно применённый принцип

Наиболее явно в проекте реализован Dependency Inversion Principle (DIP).

В internal/service/fleet.go структура Fleet работает с интерфейсом ServiceCenter.

Конкретная реализация создаётся и передаётся в internal/di/container.go.

Благодаря этому при тестировании можно заменить стандартный сервис техосмотра на FakeServiceCenter, не изменяя код Fleet.

Таким образом, DIP используется не только для формального разделения классов, но и для реальной изоляции бизнес-логики при тестировании.

5. Сознательное ограничение SOLID

Сознательно ограничен принцип Open/Closed Principle (OCP).

Добавление нового типа транспорта не требует изменения существующих методов Fleet, поскольку они работают через интерфейсы.

Однако добавление принципиально новых операций над парком может потребовать расширения самой структуры Fleet.

Например, реализация сложного расписания технического обслуживания или распределения транспорта по станциям потребует дополнительной бизнес-логики.

В данном проекте это ограничение приемлемо, поскольку приложение небольшое и предназначено для демонстрации основных сценариев учёта.

Создание отдельных стратегий и обработчиков для каждой потенциальной операции привело бы к необоснованному усложнению архитектуры.

6. Dependency Injection и контейнер

Для управления зависимостями используется пакет internal/di.

Контейнер представляет собой структуру:

type Container struct {
    ServiceCenter service.ServiceCenter
    Fleet         *service.Fleet
}

Метод NewContainer() создаёт стандартную конфигурацию приложения.

Метод NewContainerWithServiceCenter(center) позволяет передать другую реализацию ServiceCenter.

Контейнер реализован вручную, без стороннего DI-фреймворка.

Это небольшой контейнер сборки зависимостей, а не универсальный механизм автоматической регистрации и разрешения произвольных типов.

Такой подход выбран, поскольку в приложении имеется небольшое количество зависимостей и нет необходимости в сложном механизме их управления.

Подмена зависимости в тестах

Для тестирования используется FakeServiceCenter.

Он реализует тот же интерфейс ServiceCenter, но возвращает заранее заданный результат проверки.

Это позволяет проверить два сценария:

* транспорт принимается при положительном результате техосмотра;
* транспорт отклоняется при отрицательном результате.

Тест TestContainerWithFakeServiceCenter проверяет подмену зависимости через контейнер.

Тесты TestAddTransportApproved и TestAddTransportRejected проверяют поведение Fleet с подставной реализацией сервиса.

7. Расширяемость системы

Добавление нового вида транспорта

Необходимо создать новую структуру, реализующую Transport.

При необходимости структура дополнительно реализует EnergyConsumer.

Изменять существующие методы Fleet не потребуется.

Для демонстрации нового типа в консольном приложении потребуется добавить его создание в main.go.

Добавление сотрудников

Сотрудники не являются инвентарными объектами.

Поэтому для них целесообразно создать отдельную модель Employee и сервис управления сотрудниками.

Существующий учёт транспорта и инвентаря при этом не потребуется изменять.

Добавление склада запчастей

Можно создать отдельную модель склада и механизм хранения запчастей.

Если запчасти необходимо учитывать на балансе, они могут реализовывать интерфейс InventoryItem.

Для учёта остатков по нескольким складам потребуется дополнительная логика распределения объектов между складами.

Существующая предметная модель транспорта при этом может остаться без изменений.

10. Ограничения реализации

Проект является учебным прототипом и не предусматривает:

* постоянное хранение данных в базе;
* взаимодействие с реальными устройствами;
* полноценную диагностику технического состояния;
* регистрацию пользователей;
* управление арендными поездками;
* распределение транспорта между станциями.

Данные создаются в памяти при запуске программы.

Архитектура ориентирована на выполнение текущих функциональных требований с возможностью последующего расширения без преждевременного усложнения системы.
